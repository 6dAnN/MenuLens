# 云服务接入指南（替代 Dify）

> 本文说明 MenuLens 小程序如何调用 **WorkBuddy 云服务**的大模型通道。
> 原 Dify 方案保留在 `utils/api.js`，但**不再是默认路径**，也不用配任何 API Key。

---

## 一句话原理

小程序前端直接调 WorkBuddy 云服务的 LLM 接口，凭证是开通时返回的
`publicConfig`（`endpoint` + `publishableKey`）。这两个值本身不带权限，
服务端会校验请求来源，所以**不需要用户填 Key，也不需要自建后端**。

```
小程序页面
   ↓ utils/engine.js（统一入口，可切引擎）
utils/ai-cloud.js（业务编排 + 硬过滤）
   ↓ utils/cloud.js（封装 + 降级）
utils/wb-sdk.js（官方 SDK 小程序产物，内置）
   ↓ HTTPS
WorkBuddy 云服务  →  模型
```

---

## 免密钥为什么安全

| 值 | 作用 | 安全性 |
|---|---|---|
| `endpoint` | 数据平面地址 | 只是域名，不含权限 |
| `publishableKey` | 标识「哪个应用」 | 本身不带任何权限；服务端做 Origin 校验 |

真正敏感的凭据全在服务端，**永远不返回给前端**，代码里也不存在。
所以这个 Key 出现在小程序包里是设计使然，不是泄露。

> 反过来说：**永远不要把自己的服务端密钥写进小程序**。
> `_mpcheck.js` 第 9.2 项会扫描 `Bearer`/`sk-`/`app-` 形式的密钥并在发现时报错。

## 目录里各文件干什么

| 文件 | 角色 |
|---|---|
| `utils/wb-sdk.js` | 官方 SDK 的微信专用产物（166KB，已内置，导入即可用） |
| `utils/cloud.js` | 封装单例初始化、流式调用、JSON 清洗、错误翻译、用量统计 |
| `utils/ai-cloud.js` | 五项 AI 能力（菜单解析/方案/识菜/菜谱/对话）的提示词与编排 |
| `utils/engine.js` | 引擎统一入口，页面只认它 |
| `utils/api.js` | 旧 Dify 实现，保留可对比，未删除 |
| `utils/planner.js` | 本地确定性引擎，同时是硬过滤的唯一权威 |

## 为什么不需要「构建 npm」

SDK 的 `package.json#miniprogram` 字段指向一个 CommonJS 产物。官方推荐的做法是
在开发者工具里点「工具 → 构建 npm」。但那意味着**导入工程的人如果忘了这一步，
AI 会静默降级到本地引擎**，演示时很难察觉。

所以这里把该产物直接内置为 `utils/wb-sdk.js`，`cloud.js` 优先加载它，
只有内置文件缺失时才回退去 require 构建产物。升级 SDK 的方法：

```bash
npm install @tencent-ai/workbuddy-cloud-sdk@dev
cp node_modules/@tencent-ai/workbuddy-cloud-sdk/miniprogram_dist/miniprogram.js utils/wb-sdk.js
```

## 两条不能违反的规则

### 1. 过敏原过滤永远在代码层

模型**不允许**决定「这道菜能不能上桌」。顺序是：

```
hardFilter(items, ctx)  →  得到 kept（安全候选）
       ↓
模型只在 kept 里挑选 + 写理由
       ↓
assemblePlan() 二次校验：
  · 菜名必须真实存在于 kept，否则丢弃
  · 总价必须 ≤ 预算，否则丢弃
  · 缺理由则用本地 pickReason 兜底
  · 结构非法则返回 null，触发降级
```

为什么必须这样：白切鸡在菜品本体里标了含蛋，但配料写「三黄鸡」。
靠文本匹配必然漏，而漏一条过敏原在真实场景是会出事的。

`assemblePlan` 的 9 项断言在 `tests/_unittest.js` 第 11 组，逐条对着上面
这些防线。

### 2. 每条请求都必须有 system 首条消息

云服务不会替你插入默认 system，缺了直接失败。`cloud.js` 的 `chat()`
统一在最前面拼 `messages[0]`，调用方只需要传 `system` 和 `messages`。

另外该接口**只支持流式**，传 `stream:false` 会在发出网络请求前就被拒绝
（`request_stream_required`）。所以一次性任务（分类、抽取）也是流式调用
之后自己收集全文 —— `askJSON()` 就是干这个的。

## 模型选择

「我的 → AI 引擎与模型」页可以拉到当前应用的模型目录：

- `disabled: true` / `enabled: false` 的模型**不可选**，也不会被当降级目标
- 默认走目录里的默认模型（通常是 `auto`，由云服务按任务匹配）
- 看图任务（拍照识菜）建议手动选一个标了「多模态」的模型
- 目录为空是合法情况，代码会显式提示，**不会回退到写死的模型 id**

## 验证

```bash
# 云服务接入契约验证（不联网，用 wx 桩跑通 SDK 全链路）
node tests/_cloudcheck.js

# 引擎与安全断言（50 项）
node tests/_unittest.js

# 工程静态校验，含 11 项云服务接入规范
node tests/_mpcheck.js
```

`_cloudcheck.js` 会检查这 6 条契约：

1. endpoint 来自 publicConfig，未硬编码其他域名
2. 命中 `/.cloud/llm/chat/completions`
3. `stream: true` 已传
4. `messages[0]` 是 system
5. 带 publishableKey header
6. **没有** Authorization / Bearer / secret 类 header

真实连通性要在开发者工具里点「测试连接」验证——那一步走的是真网络。

## 常见问题

**Q：提示「云服务 SDK 不可用」**
A：`utils/wb-sdk.js` 被删了，或文件名大小写不对。重新复制即可。

**Q：调用一直降级到本地引擎**
A：看控制台的 `[cloud]` 开头日志。常见是网络不通，或该应用未开通云服务。
注意 demo 全链路仍然完整，只是没有真实模型推理。

**Q：想换回 Dify 对比**
A：改 `app.js` 顶部的 `const ENGINE = 'dify'`，页面代码不用动。

**Q：额度用完了**
A：报错会翻译成「额度已用完，请稍后再试」。这是账户级配额，不是代码问题。
