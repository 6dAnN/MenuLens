# 真实识菜与本地 RAG · 实现说明

这份文档讲清楚两件事：**图片识别为什么必须真看图**，以及**知识库检索为什么不用向量数据库**。
两部分都跑在 WorkBuddy 云服务上，不需要 Dify、不需要任何 API Key、不需要自建后端。

---

## 一、拍照识菜：从「套模板」到「真看图」

### 早期的问题

第一版 `recognizeDish(photoNote)` 的第二个参数名叫 `photoNote`——它接收的是一段**文字**，
发给模型的是「用户拍了一道菜，请识别」。模型没看到任何像素，只能凭上下文编一个菜名。
看起来像识别，实际是套模板，用户拍什么它都答差不多的东西。

### 现在的链路

```
wx.chooseMedia
   ↓ tempFilePath
wx.getFileSystemManager().readFile({ encoding: 'base64' })
   ↓ base64
cloud.resolveVisionModel()          ← 从云端模型目录里挑 supportsImages 的模型
   ↓ modelId
messages: [ { type:'text', text:'请识别…' },
            { type:'image_url', image_url:{ url:'data:image/jpeg;base64,…' } } ]
   ↓ 流式（云服务只支持 stream:true）
模型返回 JSON
   ↓
ai-cloud.normalizeVisionDish()      ← 归一化 + 夹紧 + 白名单收敛
   ↓
dishes.js 结构的菜品档案 → 识菜页渲染
```

四个关键点：

**1. 视觉模型必须真的支持图片。**
`resolveVisionModel()` 先读云端模型目录，筛 `supportsImages === true && selectable`。
用户若在「AI 设置」里手动选过视觉模型，必须验证它还在视觉列表里——模型下线或改名后
不能硬用一个不可用的 id，要退回目录里的视觉默认。

本机实测可用的视觉模型有 21 个（`auto` / `glm-5.3` / `deepseek-v4-pro` / `kimi-k3` 等），
默认用 `auto`——它是服务端路由模型，带图请求最稳。

**2. 图片以内容块形式进 messages，不是拼进字符串。**
必须用 OpenAI 兼容的多模态格式：

```js
content: [
  { type: 'text', text: '请识别这道菜，按约定格式输出 JSON。' },
  { type: 'image_url', image_url: { url: 'data:image/jpeg;base64,' + b64 } }
]
```

**3. 提示词强制模型交代「它看到了什么」和「它没把握什么」。**

| 字段 | 提示词约束 | 用途 |
|---|---|---|
| `confidence` | 照片模糊、只拍局部、菜太常见难区分时给 0.4 以下 | 页面上那个百分比 |
| `evidence` | 必须是真的从图里看到的，不许写「根据菜品特征」这种套话 | 「模型看到的线索」卡片 |
| `uncertainty` | 一句话说明哪里看不清、可能判错 | 黄色提示条 |
| `alternatives` | 拿不准时给最多 2 个候选 | 「也可能是」 |

只问「这是什么菜」得到的是一个自信的猜测；追问「盘子里有没有花生米」，才能让用户
自己判断这个答案靠不靠谱。

**4. 归一化必须防御性写。**
模型返回的字段名不完全固定（`flavor_text` / `flavorText` / `desc` 都可能），
数值也可能越界或非法：

- `confidence` 强制落在 `[0, 1]`；非数字回落 0.5；字符串数字（`"0.7"`）要能解析；
- `allergens` 必须收敛到固定白名单（花生 / 坚果 / 海鲜 / 甲壳类 / 乳制品 / 麸质 / 蛋 / 大豆），
  模型的自由用词（「虾」「牛奶」「小麦」）要映射进去——**过敏原集合不收敛，代码层的硬过滤就匹配不上**；
- `alternatives` 最多 2 个，`evidence` 最多 3 条，防止模型输出长列表撑破 UI。

### 真实效果

用一张清汤牛肉粉的照片实测：

```
name=越南牛肉河粉 / Pho Bo     confidence=0.82     category=汤  cuisine=越南菜
ingredients=河粉、生烫牛肉片、青葱、香菜、牛骨清汤、炸蒜
allergens=麸质、大豆
evidence=["白碗中清汤浸白色宽河粉","表面铺粉红色生烫牛肉片","撒有大量葱花香菜和葱段"]
uncertainty=牛肉片看似生烫，也可能是猪肉片，且非越南馆子也可能只是普通牛肉汤粉
alternatives=["牛肉汤河粉","清汤牛肉米粉"]
```

同一张图隔一会儿再跑，输出是「牛肉粉 / 0.72 / 主食」。

**两次结果不同不是 bug。** 模型对同一张照片的把握本来就不是固定值，
这恰恰证明了 `uncertainty` 字段的必要性——它自己都在说「可能是猪肉片」。

## 二、RAG：为什么 26 条 chunk 不该建向量数据库

### 判断依据

| 维度 | 建向量库 | 本地 BM25 |
|---|---|---|
| 语料规模 | 需要几百条以上才有明显优势 | 几十条到几百条都够用 |
| 延迟 | 一次嵌入请求 + 一次检索请求 | 毫秒级，无网络往返 |
| 成本 | 每条语料都要算嵌入 token | 零 |
| 断网 | 完全不可用 | 照常工作 |
| 可解释 | 只有相似度分数 | 标题 + 分数，能直接展示给用户 |

当前语料 26 条 chunk、约 12K 字符。建向量库的收益远小于它的四次网络往返。

### 实现

`tools/build-kb.js` 把 `knowledge/*.md` 编译成 `miniprogram/utils/kb-data.js`：

- 按 `## 标题` 切 chunk，`---` 当分隔符丢弃，文件头的说明文字不进 chunk；
- 每个 chunk 额外抽 `keywords`（主要食材 / 过敏原 / 菜系），检索时加权。

`utils/rag.js` 做检索，三个设计点：

**1. 中文分词用「单字 + 二元组」双路。**

中文没有空格，`麻婆豆腐` 到底是一个词还是四个字？
不做分词器的情况下，用单字保召回、bigram 保精度：

```
'干炒牛河的河粉为什么粘锅'
→ 干, 干炒, 炒, 炒牛, 牛, 牛河, 河, 河粉, 粉, ... , 粘锅, 锅
```

单字保证「粘锅」这种词也能命中；bigram 保证「天气」不会因为「天」出现在某道菜描述里
就被当成相关。停用词（的 / 了 / 吗 / 什么 / 怎么 …）直接剔除。

**2. BM25 打分，带词频饱和与长度归一化。**

```
score(q) = Σ idf(t) · (tf · (k1+1)) / (tf + k1 · (1 - b + b · |d|/avgdl))
```

`k1 = 1.5`、`b = 0.75`。词频饱和保证同一个词出现 10 次不会比出现 3 次高 3 倍分；
长度归一化保证长文档不会因为词汇多而占便宜。

**3. 相关性闸门——这一条最重要。**

只靠 BM25 会误召回。实测踩过的坑：

| 问题 | 未加闸门时的误召回 | 原因 |
|---|---|---|
| 今天股市怎么样 | 常见菜品问答速查(6.79) | 「天」「怎」「么」单字蒙上 |
| 明天天气如何 | 干炒牛河(4.08) | 「天」「气」在菜品描述里出现 |
| 帮我写一段 Python 代码 | 番茄炒蛋(3.29) | 「帮」这类泛化字命中 |

闸门规则：

- 必须命中**至少 34%** 的问题词项（coverage）；
- 必须命中**至少一个 bigram**（纯单字蒙上的不算）；
- 问题里没有任何词出现在语料中 → 直接返回空。

加上闸门后，上面三个问题全部召回空，模型会据实说「我这边没有确切资料」，
而不是拿一段不相关的菜谱硬答。

**4. 标题锚点。**

用户明确说出菜名时，那条 chunk 必须排第一。这里有两个坑：

- **加成值不能太小**：`常见菜品问答速查` 这种泛化条目靠零散词项能堆到 20 分以上，
  加成取 12 时还是压不过。实测取 **25**（高于泛化条目的 BM25 上限）；
- **要做双向包含判断**：知识库标题常带修饰（「泰式冬阴功」「蒜蓉炒时蔬」），
  用户只说「冬阴功」「炒时蔬」。单向 `question.indexOf(title)` 会漏掉一大类，
  所以要反过来判断「标题的核心词是否被提到」+「问题里的片段是否是标题的一部分」。

### 检索结果怎么进 prompt

`composeMessages()` 的顺序：

```
[历史轮次 最多 6 条]
[user] 【资料】（来自 MenuLens 食品知识库，回答时优先依据这些）
       【资料 1：宫保鸡丁】…
       【资料 2：常见菜品问答速查】…

       【当前菜单】…
       【用餐条件】2 人，预算 ¥200，辣度 中辣，忌口/过敏：香菜、海鲜

       用户问：宫保鸡丁含花生吗
```

**资料放在本轮 user 消息里，不放 system。** 这样每一轮模型都要重新看资料，
不会被上一轮的回答带偏。

### UI 上把依据摊开

聊天页每条回答下面有一个「▸ 依据 3 条」，点开显示：

```
宫保鸡丁                菜品知识库.md · 匹配度 47.6
常见菜品问答速查        食材与过敏原知识.md · 匹配度 19.7
八大常见过敏原          食材与过敏原知识.md · 匹配度 15.5
```

这是「AI 说的话可核查」的落地。用户不满意可以直接看它到底依据了什么。

## 三、语料怎么维护

```bash
# 改完 knowledge/*.md 后重建索引
node tools/build-kb.js

# 校验是否最新（不改文件，CI 用）
node tools/build-kb.js --check
```

`kb-data.js` 是生成产物，**不要手改**。它入库是为了让小程序导入即跑——微信小程序
不能读 md 文件，语料必须以 JS 模块形式存在于工程里。

### 扩充语料的建议

- **每道菜一个 `##` chunk**，标题写菜名。表格里必须有「主要食材」和「过敏原」两行，
  `build-kb.js` 靠这两行抽关键词；
- **不要写太长**。一个 chunk 控制在 300-600 字，太长会稀释 BM25 打分，
  检索精度反而下降；
- **主题型知识单独成 chunk**（营养建议、辣度改造、场景搭配），它们的标题会被
  标题锚点逻辑匹配到。

## 四、当前边界

诚实说明这套东西还做不到什么：

| 局限 | 现状 | 补充方向 |
|---|---|---|
| 语料只覆盖 15 道菜 | 菜单里其他菜只能靠模型的世界知识 | 首期扩到 500 道，这是最容易被低估的工作量 |
| 模型对同一张图结果不完全稳定 | 已通过 `evidence` / `uncertainty` 让不确定性可见 | 不改；稳定性换不来真实 |
| 中文分词不是真分词 | 单字 + bigram 对短问题够用，长句会稀释 | 语料上千条后再考虑接分词器或嵌入 |
| 同一道菜在不同店做法不同 | 模型会给「可能是 X」 | 提示词已要求给 alternatives |
| 过敏原只信菜品本体标注 | 这是刻意的：配料文本匹配必然漏 | 不改。宁可漏报也要让用户去问服务员 |
