# 真实识菜与本地 RAG · 实现说明

这份文档讲清楚两件事：**图片识别为什么必须真看图**，以及**知识库检索为什么不用向量数据库**。
两部分都跑在 WorkBuddy 云服务上，不需要 Dify、不需要任何 API Key、不需要自建后端。

---

## 一、拍照识菜：从「套模板」到「真看图」

### 早期的问题

第一版 `recognizeDish(photoNote)` 的第二个参数名叫 `photoNote`——它接收的是一段**文字**，
发给模型的是「用户拍了一道菜，请识别」。模型没看到任何像素，只能凭上下文编一个菜名。
看起来像识别，实际是套模板，用户拍什么它都答差不多的东西。

### 现在的链路

```
wx.chooseMedia
   ↓ tempFilePath
wx.getFileSystemManager().readFile({ encoding: 'base64' })
   ↓ base64
cloud.resolveVisionModel()          ← 从云端模型目录里挑 supportsImages 的模型
   ↓ modelId
messages: [ { type:'text', text:'请识别…' },
            { type:'image_url', image_url:{ url:'data:image/jpeg;base64,…' } } ]
   ↓ 流式（云服务只支持 stream:true）
模型返回 JSON
   ↓
ai-cloud.normalizeVisionDish()      ← 归一化 + 夹紧 + 白名单收敛
   ↓
dishes.js 结构的菜品档案 → 识菜页渲染
```

四个关键点：

**1. 视觉模型必须真的支持图片。**
`resolveVisionModel()` 先读云端模型目录，筛 `supportsImages === true && selectable`。
用户若在「AI 设置」里手动选过视觉模型，必须验证它还在视觉列表里——模型下线或改名后
不能硬用一个不可用的 id，要退回目录里的视觉默认。

本机实测可用的视觉模型有 21 个（`auto` / `glm-5.3` / `deepseek-v4-pro` / `kimi-k3` 等），
默认用 `auto`——它是服务端路由模型，带图请求最稳。

**2. 图片以内容块形式进 messages，不是拼进字符串。**
必须用 OpenAI 兼容的多模态格式：

```js
content: [
  { type: 'text', text: '请识别这道菜，按约定格式输出 JSON。' },
  { type: 'image_url', image_url: { url: 'data:image/jpeg;base64,' + b64 } }
]
```

**3. 提示词强制模型交代「它看到了什么」和「它没把握什么」。**

| 字段 | 提示词约束 | 用途 |
|---|---|---|
| `confidence` | 照片模糊、只拍局部、菜太常见难区分时给 0.4 以下 | 页面上那个百分比 |
| `evidence` | 必须是真的从图里看到的，不许写「根据菜品特征」这种套话 | 「模型看到的线索」卡片 |
| `uncertainty` | 一句话说明哪里看不清、可能判错 | 黄色提示条 |
| `alternatives` | 拿不准时给最多 2 个候选 | 「也可能是」 |

只问「这是什么菜」得到的是一个自信的猜测；追问「盘子里有没有花生米」，才能让用户
自己判断这个答案靠不靠谱。

**4. 归一化必须防御性写。**
模型返回的字段名不完全固定（`flavor_text` / `flavorText` / `desc` 都可能），
数值也可能越界或非法：

- `confidence` 强制落在 `[0, 1]`；非数字回落 0.5；字符串数字（`"0.7"`）要能解析；
- `allergens` 必须收敛到固定白名单（花生 / 坚果 / 海鲜 / 甲壳类 / 软体类 / 乳制品 / 麸质 / 蛋 / 大豆 / 芝麻），
  模型的自由用词（「虾」「牛奶」「小麦」）要映射进去——**过敏原集合不收敛，代码层的硬过滤就匹配不上**；
- `alternatives` 最多 2 个，`evidence` 最多 3 条，防止模型输出长列表撑破 UI。

**5. 候选清单注入 + 知识库对账（第二版新增）。**

识别的精准度不只是模型的事。做了两件事把错的空间压窄：

**① 不问「这是什么」，改问「这最像清单里的哪个」。**
知识库有 731 道菜，但不会全塞进提示词——那要一万多 token，模型面对长列表反而
更容易随手挑一个。做法是从 `dish-match.candidateList()` 取 **40 个候选**
（模型自己给的 alternatives 优先，其次老库高频菜，再按菜系聚类补齐），
拼在提示词前面，并要求：能在清单里找到就**原样照抄标准菜名**，找不到才自己起名
并把 `in_kb` 置 false。

**② 模型输出必须过一遍代码对账，`utils/dish-match.js`。**

模型给的菜系、辣度、过敏原都只当**线索**，与知识库记录冲突时以知识库为准，
并按冲突程度**下调置信度**：

| 情况 | 处理 | 置信度折扣 |
|---|---|---|
| 菜名完全一致 | 不改 | ×1.00 |
| 菜名英文名 / 别名匹配 | 归一为标准名 | ×0.95 |
| 菜名包含关系（「冬阴功」→「泰式冬阴功」） | 归一 | ×0.94 |
| 菜名错别字（「宫爆鸡丁」→「宫保鸡丁」） | 归一 | ×0.88 |
| 菜系与知识库不符 | 改成知识库的 | ×0.90 |
| 辣度差一档以上 | 改成知识库的 | ×0.95 |
| 知识库没有这道菜 | 保留模型判断，UI 标注「无权威资料」 | ×0.82 |

菜名归一用了五级匹配：标准名 → 核心名（去括号去修饰）→ 英文名 → 包含关系 → **编辑距离**。
最后一级为什么不用 bigram Jaccard：「宫爆鸡丁」vs「宫保鸡丁」的二元组只共享「鸡丁」，
Jaccard 只有 0.25 会被阈值挡掉；但中文菜名错字几乎都是**同音替换单字**，
长度不变、只有一个字不同——编辑距离才是对的度量。

**过敏原取并集，不是取模型说的那些。** 知识库记录的绝不能因为模型没提到就丢，
这是硬过滤的输入。模型多给的也保留（宁多勿少）。

折扣后的两个数都摊开给用户看：识菜页点「置信度」会说明
「视觉模型自评 X%，与知识库对账后调整为 Y%」，并列出更正了哪些字段、为什么下调。


### 真实效果

用一张清汤牛肉粉的照片实测：

```
name=越南牛肉河粉 / Pho Bo     confidence=0.82     category=汤  cuisine=越南菜
ingredients=河粉、生烫牛肉片、青葱、香菜、牛骨清汤、炸蒜
allergens=麸质、大豆
evidence=["白碗中清汤浸白色宽河粉","表面铺粉红色生烫牛肉片","撒有大量葱花香菜和葱段"]
uncertainty=牛肉片看似生烫，也可能是猪肉片，且非越南馆子也可能只是普通牛肉汤粉
alternatives=["牛肉汤河粉","清汤牛肉米粉"]
```

同一张图隔一会儿再跑，输出是「牛肉粉 / 0.72 / 主食」。

**两次结果不同不是 bug。** 模型对同一张照片的把握本来就不是固定值，
这恰恰证明了 `uncertainty` 字段的必要性——它自己都在说「可能是猪肉片」。

## 二、RAG：为什么不建向量数据库

### 判断依据

| 维度 | 建向量库 | 本地 BM25 |
|---|---|---|
| 语料规模 | 需要几百条以上才有明显优势 | 几百到上千条都够用 |
| 延迟 | 一次嵌入请求 + 一次检索请求 | 毫秒级，无网络往返 |
| 成本 | 每条语料都要算嵌入 token | 零 |
| 断网 | 完全不可用 | 照常工作 |
| 可解释 | 只有相似度分数 | 标题 + 分数，能直接展示给用户 |

**语料扩到 740 条之后，这个判断依然成立。** 实测索引构建 46ms（只在首次检索时发生），
之后单次检索 **1.4ms**，索引常驻内存。这个规模下向量库的唯一优势是语义泛化，
而这里用同义词扩展 + 标题锚点补上了，代价是零网络往返。

### 语料规模

| 项 | 数值 |
|---|---|
| 菜品 | 731 道（19 个菜系分组） |
| 主题知识 | 10 条（过敏原 / 人群 / 辣度 / 点单原则 / 酒水 …） |
| chunk 总数 | 740 |
| 编译后体积 | 524 KB（`kb-data.js`） |
| 首次索引 | 46 ms |
| 单次检索 | 1.4 ms |
| 检索质量 | 37/37 正确命中，5/5 无关问题正确拒绝 |

### 语料怎么来的：种子数据 → 校验 → 生成

不是手写 markdown，走三层流水线：

```
tools/kb-seed-data/*.js     逐菜一行的种子数据（19 个菜系文件，| 分隔 17 字段）
        ↓  tools/kb-seed.js     校验 + 渲染成 markdown
knowledge/菜品知识库-1~4.md   人可读，按 200 道分卷
        ↓  tools/build-kb.js    切 chunk + 抽 keywords
miniprogram/utils/kb-data.js  小程序读的模块
        ↓  tools/build-demo-kb.js
demo/kb.js                    H5 读的 IIFE（带完整检索算法）
```

**校验是硬性的，不生成半成品。** `kb-seed.js` 会拦下：

- 字段数不对（行格式被手误打乱）——这类错误最容易发生，也最难肉眼发现
- 过敏原不在白名单里
- 辣度 / 难度越界
- 菜名重复（同一道菜写进了两个菜系卷）
- 缺描述、缺食材

错误直接 `exit 1` 并打印第几行第几个字段。

**为什么用「一菜一行」而不是直接写 markdown**：731 道菜如果用表格写 md，
改一行要数 17 个竖线；一行式种子文件让 diff 干净、字段错位立刻在字段数校验里炸掉。

**为什么 `build-demo-kb.js` 要内联 `rag.js` 而不是重写一遍**：
两个前端必须**算法同源**。脚本读 `rag.js` 源码、去掉 CommonJS 头尾、包进 IIFE。
如果只复制逻辑，改了一边忘了另一边，「小程序搜得到、H5 搜不到」这种问题查不完。

### 实现

`utils/rag.js` 做检索，五个设计点：


**1. 中文分词用「单字 + 二元组」双路。**

中文没有空格，`麻婆豆腐` 到底是一个词还是四个字？
不做分词器的情况下，用单字保召回、bigram 保精度：

```
'干炒牛河的河粉为什么粘锅'
→ 干, 干炒, 炒, 炒牛, 牛, 牛河, 河, 河粉, 粉, ... , 粘锅, 锅
```

单字保证「粘锅」这种词也能命中；bigram 保证「天气」不会因为「天」出现在某道菜描述里
就被当成相关。停用词（的 / 了 / 吗 / 什么 / 怎么 …）直接剔除。

**2. BM25 打分，带词频饱和与长度归一化。**

```
score(q) = Σ idf(t) · (tf · (k1+1)) / (tf + k1 · (1 - b + b · |d|/avgdl))
```

`k1 = 1.5`、`b = 0.75`。词频饱和保证同一个词出现 10 次不会比出现 3 次高 3 倍分；
长度归一化保证长文档不会因为词汇多而占便宜。

**3. 相关性闸门——这一条最重要。**

只靠 BM25 会误召回。实测踩过的坑：

| 问题 | 未加闸门时的误召回 | 原因 |
|---|---|---|
| 今天股市怎么样 | 常见菜品问答速查(6.79) | 「天」「怎」「么」单字蒙上 |
| 明天天气如何 | 干炒牛河(4.08) | 「天」「气」在菜品描述里出现 |
| 帮我写一段 Python 代码 | 番茄炒蛋(3.29) | 「帮」这类泛化字命中 |

闸门规则：

- 必须命中**至少 34%** 的问题词项（coverage）；
- 必须命中**至少一个 bigram**（纯单字蒙上的不算）；
- 问题里没有任何词出现在语料中 → 直接返回空。

**但语料扩到 740 条之后，闸门单独不够用了。** 多了一个意图闸门和一个同义词通道：

**意图闸门。** 「香港旅游攻略」会靠 bigram「香港」命中「盐焗鸡（港式）」「丝袜奶茶」——
它确实命中了真实词项，三道闸门都拦不住。所以先判意图：

```js
const OFF_TOPIC = /(攻略|旅游|景点|机票|酒店|签证|天气|股票|基金|汇率|编程|代码|考试|论文|招聘|简历)/;
const FOOD_HINT = /(菜|吃|点|辣|过敏|食材|做|煮|炒|蒸|味|口感|热量|价格|推荐|搭配|饭店|餐厅|忌口)/;
if (OFF_TOPIC.test(query) && !FOOD_HINT.test(query)) return [];
```

出现非饮食词、且**没有**任何饮食词 → 直接不进检索。两个条件都要满足，
所以「这菜辣不辣，会不会上火」不会被误拦。

**同义词通道。** 用户不会说「点单搭配原则」，他说「三个人三百块怎么点菜」；
也不会说「营养成分与人群建议」，他说「孕妇能吃什么」。
分词得到「点菜」，语料标题是「点单」，**一个 bigram 都不共享**，会被闸门拦掉。

所以加了一张显式的口语 → 语料用词映射表（`SYNONYM`，八类：点单 / 人群 / 过敏 /
辣度 / 价格 / 热量 / 搭配 / 酒水）。命中的同义词项按 **0.6 权重**叠加，
并单独计 `synHit` 走独立放行路径——**不计入 bigram 闸门**，否则「点菜」这个
bigram 会蒙上一堆讲做法的条目。

**覆盖度加成。** 这是最后一个查出来的问题。
「孕妇能吃生鱼片吗」最初召回「口水鱼片 / 艇仔粥 / 生滚粥」——全错了。
原因不是闸门，是 BM25 的一个反直觉性质：**文档越长，同样词频的得分被压得越低**。
「孕妇」只出现在 1200 字的「营养成分与人群建议」里，裸分 17.3；
而「口水鱼片」靠「生/鱼/鱼片/片」这种到处都有的字，因为文档短反而拿到 21.5。

修法不是调 BM25 参数（那会连带影响所有查询），而是承认**覆盖度是独立信号**：
命中 ≥2 个问题词项的文档，按「命中数 / 问题词项数」给一笔加成。

**标题锚点。**

用户明确说出菜名时，那条 chunk 必须排第一。这里有两个坑：

- **加成值不能用固定常数**。早先取 +25，在 26 条语料下刚好够（泛化条目裸分上限约 22）。
  扩到 740 条后，泛化条目会同时命中好几个词，裸分涨到 46，固定 25 就失效了。
  改成**相对加成**：`anchorBase = 本次最高裸分 × 1.3 + 5`，与语料规模无关；
- **要做双向包含判断**：知识库标题常带修饰（「泰式冬阴功」「蒜蓉炒时蔬」），
  用户只说「冬阴功」「炒时蔬」。单向 `question.indexOf(title)` 会漏掉一大类，
  所以要反过来判断「标题的核心词是否被提到」+「问题里的片段是否是标题的一部分」。

### 检索结果怎么进 prompt

`composeMessages()` 的顺序：

```
[历史轮次 最多 6 条]
[user] 【资料】（来自 MenuLens 食品知识库，回答时优先依据这些）
       【资料 1：宫保鸡丁】…
       【资料 2：常见菜品问答速查】…

       【当前菜单】…
       【用餐条件】2 人，预算 ¥200，辣度 中辣，忌口/过敏：香菜、海鲜

       用户问：宫保鸡丁含花生吗
```

**资料放在本轮 user 消息里，不放 system。** 这样每一轮模型都要重新看资料，
不会被上一轮的回答带偏。

### UI 上把依据摊开

聊天页每条回答下面有一个「▸ 依据 3 条」，点开显示：

```
宫保鸡丁                菜品知识库.md · 匹配度 47.6
常见菜品问答速查        食材与过敏原知识.md · 匹配度 19.7

```

这是「AI 说的话可核查」的落地。用户不满意可以直接看它到底依据了什么。

## 三、语料怎么维护

```bash
# 1. 改种子数据（一菜一行，| 分隔 17 字段）
#    tools/kb-seed-data/*.js，按菜系分文件，19 个分组在 index.js 里登记

# 2. 校验 + 渲染成 markdown
node tools/kb-seed.js

# 3. 只校验不写文件（CI 用）
node tools/kb-seed.js --check

# 4. 编译成小程序读的模块
node tools/build-kb.js

# 5. 同步一份给 H5 demo
node tools/build-demo-kb.js
```

`kb-data.js` 和 `demo/kb.js` 都是生成产物，**不要手改**。它们入库是为了让
小程序/H5 导入即跑——微信小程序读不了 md，浏览器 `file://` 下也读不了。

### 种子数据的行格式

17 个字段，`|` 分隔：

```
name|en|cuisine|region|cat|role|price|diff|time|spicy|ingredients|methods|allergens|light|umami|ma|desc
菜名|英文名|菜系|产地|类别|定位|价格区间|难度1-5|耗时分钟|辣度0-3|主要食材|烹饪方式|过敏原|清淡度|鲜香度|麻度|描述
```

**`desc` 是整个语料里最值钱的字段。** 它不是给人看的产品文案，是**给视觉模型的判别线索**：

> 红亮红油浸嫩白豆腐块、表面撒棕红花椒粉与蒜苗末。豆腐一夹就断、麻在舌尖、辣在后段。

写「怎么认 + 什么味」，不写「历史悠久、深受喜爱」。模型拿着这句话去比对自己看到的像素，
判断依据就是这句话。

### 扩充语料的建议

- **每道菜一个 chunk**，标题写标准菜名。表格里必须有「主要食材」和「过敏原」两行，
  `build-kb.js` 靠这两行抽关键词；
- **描述控制在 40-80 字**。太短没有判别力，太长会稀释 BM25 打分；
- **主题型知识单独成 chunk**（营养建议、辣度改造、场景搭配），它们的标题会被
  标题锚点逻辑匹配到；
- **过敏原必须落在白名单里**：`花生 / 坚果 / 海鲜 / 甲壳类 / 软体类 / 乳制品 / 麸质 / 蛋 / 大豆 / 芝麻`。
  写「虾」会被拒——因为代码层的过滤是精确匹配。

## 四、当前边界

诚实说明这套东西还做不到什么：

| 局限 | 现状 | 补充方向 |
|---|---|---|
| 语料覆盖 731 道 | 超出范围只能靠模型的世界知识，UI 会标注「知识库未收录」 | 按需继续扩；采集比模型选型更耗时 |
| 模型对同一张图结果不完全稳定 | 已通过 `evidence` / `uncertainty` 让不确定性可见 | 不改；稳定性换不来真实 |
| 中文分词不是真分词 | 单字 + bigram 对短问题够用，长句会稀释 | 靠 `SYNONYM` 表补口语落差，可继续加词条 |
| 同一道菜在不同店做法不同 | 模型会给「可能是 X」，对账会纠错别字与菜系 | 提示词已要求给 alternatives |
| 过敏原只信菜品本体标注 | 这是刻意的：配料文本匹配必然漏 | 不改。宁可漏报也要让用户去问服务员 |
| 同义词表是手工维护的 | 新口语说法要人工补一行 | 它是产品资产，不是临时补丁 |
